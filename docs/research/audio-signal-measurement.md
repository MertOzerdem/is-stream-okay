# Audio signal measurement research

Reviewed 2026-10-28 for [ticket 06](../../.scratch/is-stream-okay/issues/06-audio.md).

## Findings from primary sources

- **Player APIs are not sample meters.** Twitch documents `getVolume()` as a player setting from 0.0 to 1.0, alongside mute controls and playback statistics; it does not document a PCM waveform API. Kick's public embed guide documents `autoplay` and `muted` URL parameters, but no JavaScript sample-reading API. The HTML Standard says media volume is relative, and its range need not be linear. These values cannot stand in for the stream's digital signal level. ([Twitch Embed API](https://dev.twitch.tv/docs/embed/video-and-clips), [Kick embed guide](https://help.kick.com/en/articles/8010826-how-to-embed-your-kick-livestream), [HTML Standard: media volume and mute](https://html.spec.whatwg.org/multipage/media.html))
- **A server-owned browser can target the player frame.** The HTML same-origin model prevents the host page's script from inspecting a cross-origin iframe's document. Playwright's `Frame.evaluate()` runs code in the selected frame's page context; this is the relevant server-side seam for inspecting a player element, and is separate from what ordinary page JavaScript may access. The existing probes already select Twitch/Kick frames. ([HTML Standard: origins](https://html.spec.whatwg.org/multipage/browsers.html), [Playwright Frame](https://playwright.dev/docs/api/class-frame))
- **Web Audio can analyze a media element, subject to media-resource CORS.** `MediaElementAudioSourceNode` re-routes an `audio` or `video` element's audio into an audio graph, and `AnalyserNode.getFloatTimeDomainData()` exposes recent waveform samples. However, if Fetch labels the media resource CORS-cross-origin, the Web Audio specification requires the source node to output silence even while the HTML media element can play that resource. Therefore, access to the iframe/video element alone does not prove that decoded samples are inspectable. The platform's public embed guides do not guarantee the CORS status of their live media pipeline. ([Web Audio API: media element source security](https://webaudio.github.io/web-audio-api/), [Web Audio API: analyser](https://webaudio.github.io/web-audio-api/), [HTML Standard: CORS settings](https://html.spec.whatwg.org/multipage/urls-and-fetching.html))
- **Muted autoplay and audio-context state can look like silence.** Twitch and Kick both expose a muted start option. HTML defines a muted media element's effective media volume as zero; user agents may allow muted playback without transient user activation, but the standard does not require autoplay to work in every context. Twitch also documents `PLAYBACK_BLOCKED`, commonly after unmuted autoplay/programmatic playback. Web Audio contexts start suspended, and while suspended media-element output is ignored and repeated analyser reads return the same data. A zero meter must not be classified as a silent stream until the player is actually playing, the context is running, and the player is not suppressing its audio. ([Twitch Embed API](https://dev.twitch.tv/docs/embed/video-and-clips), [Kick embed guide](https://help.kick.com/en/articles/8010826-how-to-embed-your-kick-livestream), [HTML Standard: autoplay and media playback](https://html.spec.whatwg.org/multipage/media.html), [Web Audio API](https://webaudio.github.io/web-audio-api/))
- **The analyser gives normalized digital samples, not acoustic sound pressure.** Web Audio exposes script-visible audio as linear 32-bit float PCM. `getFloatTimeDomainData()` returns the most recent `fftSize` frames after down-mixing to mono. For a window of samples `x[k]`, an implementation can define `RMS = sqrt(sum(x[k]^2) / N)` and `dBFS = 20 * log10(RMS / 1.0)`; zero RMS is mathematically `-Infinity`, so the UI should display a documented measurement floor or “below measurement floor.” The Web Audio spec defines amplitude-to-decibel conversion as `20 * log10(v)`. This is a digital level relative to full-scale amplitude 1.0, not calibrated dB SPL and not a promise that a person can hear the stream in a particular room or device. ([Web Audio API](https://webaudio.github.io/web-audio-api/))
- **Use one monotonic clock for elapsed measurement.** High Resolution Time specifies a monotonic clock that is not changed by wall-clock adjustments and recommends it for measurement. Keep audio sampling timestamps within the same frame/context; do not compare unrelated time origins as if they were absolute. ([W3C High Resolution Time](https://www.w3.org/TR/hr-time-3/))

## Implementation implications (inference)

1. In the server-side Playwright frame, locate the active media element, create one `MediaElementAudioSourceNode`, and route it through an `AnalyserNode`. The selected player is unmuted and set to full element volume for a consistent stream-level reading. Route the graph through a zero-gain node and launch Chromium with `--mute-audio` so the worker does not emit sound.
2. Start only after the media element is playing and `AudioContext.state` is `running`. The browser fixture verifies that known PCM reaches the analyser. On Chromium, use `webkitAudioDecodedByteCount` as extra evidence: all-zero analyser data with decoded bytes from an unrecognized cross-origin URL is ambiguous, so report measurement unavailable; the current Twitch and Kick players use a `MediaSourceHandle`, and both produced non-zero samples in live probes. A suspended context or failed/incomplete sample coverage also means unavailable.
3. Use an `AudioWorklet` to accumulate non-overlapping 2048-frame chunks and mean-square RMS across the observation. If worklets are unavailable, fall back to 2048-frame analyser windows every 35 ms. Report only when sample coverage is at least 90%. The first-version classification is a product heuristic: below −60 dBFS is “no signal,” from −60 to below −35 dBFS is “very low,” and −35 dBFS or above is “signal detected.” The specifications define the dBFS math, not these category boundaries.
4. Keep result language about **digital signal level / signal detected**. Labels such as “audible in a quiet room” would claim physical audibility that this server-side digital measurement does not establish. Codec identity may inform a separate compression note but does not calibrate or predict measured dBFS.

## Limits and validation status

The signal path is standards-supported, but availability for Twitch and Kick is not guaranteed by their public embed documentation. Controlled same-origin PCM WAV fixtures at digital silence, −45 dBFS RMS, and −20 dBFS RMS returned the expected classes and levels. With the final AudioWorklet path, live 30-second probes returned −31.1 dBFS for Twitch and −8.4 dBFS for Kick, each with 99.9% sample coverage. The player frames reported `MediaSourceHandle` and increasing decoded-audio byte counts on both platforms. Revalidate when Chromium or either player integration changes. If the context does not run, coverage is below 90%, or decoded bytes accompany zero samples from an ambiguous cross-origin source, return “measurement unavailable.”

## Evidence versus inference

The iframe origin rules, player options/API fields, media-element source behavior, mandatory silence for CORS-cross-origin resources, analyser sample semantics, and monotonic-clock behavior above are documented facts. The `MediaSourceHandle` and `webkitAudioDecodedByteCount` observations, player-frame measurements, 2048-frame chunk size, 35 ms fallback cadence, coverage cutoff, dBFS thresholds, and fallback classification are empirical or implementation choices, not guarantees from the platform embed documentation.
